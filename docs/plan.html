01

What the agent actually answers

The investment question is not "which airport is busy" — it is where is demand pressing against a physical constraint that concrete can relieve. Busy-and-roomy is a bad deal. Constrained-and-shrinking is a worse one. The target is constrained, growing, and structurally under-built.

So the core output is a single deterministic index, the Renovation Upside Score (RUS, 0–100), decomposed into five named components an analyst can argue with. The LLM never produces the number. It picks the tool, sets the filters, and explains the arithmetic it was handed.

Rank

Peer-normalised RUS across any region, hub class, or state filter.

Compare

Head-to-head on all five components plus raw operational inputs.

Diagnose

Why a score is what it is: which input drove it, and how sure we are.

03

Scoring methodology

Five components, each computed in TypeScript from DuckDB aggregates, each winsorised at the 5th/95th percentile then min–max normalised within the airport's hub class so a small airport is scored against small airports, not against ATL.

RUS = 100 × ( 0.30·CPI + 0.25·HCD + 0.20·DMI + 0.15·UDI − 0.10·RSK ) clamped [0,100] CPI Congestion Pressure = n(avg dep delay) · .35 + n(taxi-out p80) · .30 + n(peak-hour movements ÷ runways) · .35 HCD Headroom Deficit = n(annual movements ÷ (runways × 200k)) · .5 + n(enplanements ÷ runways) · .5 DMI Demand Momentum = n(enplanement CAGR 2023→25) · .6 + n(growth 2024→25) · .4 UDI Unmet Demand = n(pax per departure) · .4 + n(cancel + divert rate) · .3 + n(catchment pop per enplanement) · .3 RSK Risk / feasibility = n(carrier HHI) · .5 + n(weather + airspace share of delay) · .5 ← subtracted n(x) = winsorise at the 5th/95th percentile of the airport's FAA hub class, then min–max scale to 0–1
ComponentWeightInvestment logic
Congestion Pressure0.30Delay and taxi-out are the observable price of a constraint. Highest weight because it is the best-measured signal we have.
Headroom Deficit0.25Throughput per unit of physical plant. High deficit = the airport is doing a lot with too little, which is exactly what a build fixes.
Demand Momentum0.20Renovation pays back over 20+ years. A congested but flat airport is a trap.
Unmet Demand0.15Spilled passengers: full aircraft, cancelled flights, a catchment flying less than its population implies.
Risk penalty−0.10Single-carrier dependence and weather-driven delay both mean new concrete may not convert into new throughput.

Rules that keep the number honest

  • Peer normalisation. z-scores computed inside FAA hub class, so rankings compare like with like unless the analyst explicitly asks across classes.
  • Coverage gate. Any airport missing more than one component input gets a score of null, not a guessed one, and is listed separately as "insufficient data".
  • Confidence band. Every score ships with ± derived from input completeness and data age. A 71 ± 9 and a 71 ± 2 are different recommendations.
  • Weights are input, not code. The sliders re-score every airport in the browser, using the same module the API uses — no round trip, no model.
  • Nearest-rank winsorising. Interpolated percentiles drag the 95th of a small peer group most of the way to its largest member, which is the exact outlier the winsorising exists to fence off. The bounds pick an observed value instead. A unit test pins this: adding an airport with a 100,000-minute delay must not move a normal airport's congestion score by more than 0.15.
  • Sample floor. Delay statistics are dropped below 500 departures in the window. A 90-minute average over 40 flights is a real number and statistically empty.
  • Screening floor. Airports under 100,000 annual enplanements (or 5,000 annualised departures) are scored but held out of the default ranking, so a field with 45 flights a year cannot top a shortlist.
04

Architecture

The LLM sits at the edges — parsing intent on the way in, narrating on the way out. It never touches arithmetic and never sees raw CSV.

Runtime

  • Next.js App Router on Vercel, Node runtime (Fluid Compute).
  • AI SDK v6 streamText + tool calling, models addressed as "provider/model" through AI Gateway so the provider is swappable.
  • DuckDB is an offline ETL engine only, run over 7.0 M flight records. The runtime artifact is a single data/airports.json of raw measured metrics — small enough to hold in module scope on the server and ship to the browser, which is what makes the weight sliders instant.
  • Voice: browser SpeechRecognition in, speechSynthesis out. Bonus-tier, degrades to text silently.

Where AI is used — and where it is not

  • Is: mapping "New England" → the 6-state filter; resolving "LA and Santa Ana" → LAX/BUR/LGB and SNA; choosing which tool answers; writing the prose; carrying context across follow-ups.
  • Is not: any component value, any weight, any ranking order, any percentage. Those come from tested pure functions and are injected into the answer as structured JSON.
  • Three mechanisms enforce that line rather than trusting it. Every figure in a reply is extracted and looked for in the tool payloads, and anything unaccounted for is badged next to the answer in the UI. A model that returns figures without calling a tool is rejected outright and the deterministic answer served instead. And a "Run without the model" control answers the same question by rules over the same tools — if the two disagree, the model is wrong.
05

The four questions, walked through

Which airports in New England are strong candidates for terminal expansion?
rankAirports({ states:[ME,NH,VT,MA,RI,CT], limit:5, minEnplanements:100000 })Returns RUS-ranked list with per-component breakdown. Answer names the top 3, gives each one's dominant driver (e.g. "BDL scores on headroom deficit, not delay"), and states that terminal-specific square footage is inferred, so the ranking is about movement capacity pressure rather than gate count.
Compare LA and Santa Ana airport congestion levels.
compareAirports({ codes:[LAX, SNA], focus:"congestion" })Ambiguity handled explicitly: "LA" resolves to LAX by default, with BUR/LGB/ONT offered as a follow-up. Output is the CPI sub-table — avg departure delay, p80 taxi-out, peak-hour ops vs runway capacity — plus the live NAS Status line for each if a delay program is active right now.
What is the percentage of long-haul flights out of Anchorage?
haulMix({ code:"ANC", basis:"departures", period:"CY2024" })Great-circle distance per T-100 segment, bucketed short <1,500 km / medium 1,500–4,000 / long >4,000. Two numbers reported separately, because for ANC they diverge sharply: share of departures vs share of seats. Cargo-only segments excluded and that exclusion is stated — ANC is a top-five global freight hub and including it would triple the answer.
What is the unmet flight demand at SFO and why?
explainScore({ code:"SFO", component:"UDI" })Decomposes UDI into its three inputs with the raw values, then attributes: load factor above the peer median, cancellation rate concentrated in specific months, catchment population vs enplanements. Closes with the honest limit — this is revealed spill, not a demand model; true unmet demand needs fare and search data we do not have.
06

Key tradeoffs and what we're not claiming

Batch over live. Reproducibility and speed beat freshness for an investment screen. Cost: the dataset is a quarter stale, and the agent says so in every answer that leans on BTS.
No terminal square footage exists publicly. "Terminal expansion" is therefore scored as movement-capacity pressure. A real diligence process would buy this data; we flag it rather than fake it.
Weights are a thesis, not a fact. 0.30/0.25/0.20/0.15/−0.10 encodes a view that observable delay is the strongest constraint signal. The sliders make a disagreeing analyst one drag away from their own ranking.
Peer-class normalisation hides cross-class comparison. A small airport's 88 and a large hub's 88 mean different absolute opportunity sizes. Raw components are always shown alongside so the analyst can re-rank.
No construction cost, land, or political feasibility. RUS measures upside, not cost or buildability. It ranks candidates for a human to underwrite — it does not price the deal.
Reporting-carrier bias. BTS On-Time covers only the largest carriers, so regional-heavy airports have thinner delay data. Captured in the confidence band and the sample floor, not smoothed over.
No seats, so no true load factor. BTS killed the T-100 bulk download mid-build. Load is proxied by passengers per departure — annual enplanements over annualised departures — which conflates load factor with aircraft gauge. Labelled a proxy everywhere it appears.

Build order

Sequenced so a working end-to-end slice exists after phase 4 — if time runs out, everything after that degrades gracefully.

  1. 0.0–1.0
    Ingest
    Pull the five batch sources, normalise IATA codes, load DuckDB. Ship the .duckdb file to the repo so the build is offline-reproducible.
  2. 1.0–2.5
    Scoring core
    Pure functions for the five components + winsorise/normalise. Unit tests with known fixtures, including the null-coverage path. This is the deliverable that must be right.
  3. 2.5–3.5

    Five typed tools over the scoring core, each returning value + provenance + confidence. Callable and testable without any LLM.
  4. 3.5–5.0

    System prompt, tool wiring, streaming UI, multi-turn context. Verify all four sample questions end to end.
  5. 5.0–6.0

    Component breakdown panel, weight sliders, confidence badges, source-and-vintage line under every answer.
  6. 6.0–6.5

    Web Speech in/out behind a feature flag. Bonus — cut first if anything above slips.
  7. 6.5–8.0
    Docs + deploy
    Architecture doc, README with run instructions, Vercel deploy, README-linked worked examples of the four questions.
08

Assumptions stated up front

  • US commercial airports with scheduled passenger service only; no general-aviation, military, or territorial fields beyond PR/VI.
  • "Congestion" means departure delay, taxi-out time, and peak-hour movement rate — not TSA queue time or gate-hold, which are unpublished.
  • Runway practical capacity is approximated at 200,000 annual operations per runway, before adjusting for configuration and geometry. Crude; parallel-runway airports are consequently over-penalised and this is noted per airport.
  • Catchment is a 100 km radius sum of county population — a stand-in for drive-time isochrones.
  • Long haul is >4,000 km great-circle. The threshold is a parameter, and the agent will restate it whenever it reports a haul-mix figure.
  • Passenger and operations data are historical. Nothing here forecasts demand except FAA's own TAF, used at 0.4 of one component.

What changed once we hit the data

Four things in this plan did not survive contact with the sources. Each is recorded here rather than quietly edited out, because the substitutions are what an analyst needs to know to trust the numbers.

Runtime DuckDB Nothing needed it. The aggregate over 7.0 M flight records is ~380 rows. DuckDB stayed as the offline ETL engine; the runtime artifact is one JSON file. That removed the database, and let the browser re-score locally when a weight moves.

And three things the build added

  • A deterministic answerer. Rules read the question, call the same tools, and write the answer from a template. It is the demo's safety net with no key and no network — and the control case: if the model disagrees with it, the model is wrong.
  • A number check on every reply. Figures in the answer are matched against the tool payloads; unaccounted ones are badged in the UI. A reply with figures but no tool call is rejected before it reaches the user.
  • An identifier fix worth naming. FAA keys its enplanement file on the FAA location identifier, not IATA — Mesa Gateway is AZA to travellers and IWA to the FAA. Two airports silently lost their passenger data until the join matched on either.
Runway Alpha — plan of record. Every figure the agent reports carries its source, its vintage, and its confidence; where the data cannot answer, the agent says so instead of estimating.
